** Verified build recipe (emacs 31.1, Apple Silicon)
Verified <2026-10-13> on macOS 26 (Darwin 25.6), Apple clang 21. Same shape as
the 30.2 recipe below; only the differences are spelled out here.

*** 1. Prerequisites
Same brew list as 30.2 (gcc libgccjit make gnutls texinfo autoconf pkg-config,
plus the runtime helpers). Versions in the verified build: gcc/libgccjit 16.2.0,
make 4.4.1, texinfo 7.3, autoconf 2.73.

tree-sitter: built against =tree-sitter@0.25= (keg-only), *because 30.2 was
still installed*. Any tree-sitter >= 0.25 gives emacs 31 ABI 15 support -- the
configure floor (still 0.20.2) is not the version that matters.

Do not =brew install tree-sitter= while emacs 30.2 is still in use: 30.2 links
=opt/tree-sitter/lib/libtree-sitter.0.25.dylib= through the shim described in
gotcha #1 of the 30.2 recipe, and mainline (0.27.1 as of this writing) would
replace it.

#+begin_src sh
export PKG_CONFIG_PATH="$(brew --prefix tree-sitter@0.25)/lib/pkgconfig"
pkg-config --modversion tree-sitter    # 0.25.10
#+end_src

*** 2. Configure and build
Unchanged flag set from 30.2. etc/NEWS has no macOS-relevant installation
changes for 31.1; --with-xwidgets and --disable-gc-mark-trace both still exist.
#+begin_src sh
cd ~/bin/emacs-31.1
./autogen.sh
./configure \
    --with-native-compilation \
    --with-tree-sitter \
    --without-compress-install \
    --disable-gc-mark-trace \
    --with-xwidgets
gmake -j"$(sysctl -n hw.ncpu)"
#+end_src
Configure summary reported yes for -ltree-sitter, Xwidgets and native lisp
compiler.

*** 3. Verify
#+begin_src sh
src/emacs -Q --batch --eval '(progn
  (princ (format "treesit:     %s\n" (treesit-available-p)))
  (princ (format "abi:         %s / min %s\n" (treesit-library-abi-version) (treesit-library-abi-version t)))
  (princ (format "native-comp: %s\n" (native-comp-available-p)))
  (princ (format "xwidgets:    %s\n" (fboundp (quote make-xwidget)))))'
otool -L src/emacs | grep -E 'tree-sitter|gccjit'
#+end_src
Result of the verified build:
#+begin_src

native-comp: t
xwidgets:    t
/opt/homebrew/opt/libgccjit/lib/gcc/current/libgccjit.0.dylib

#+end_src
Feature list is identical to the 30.2 build. Note tree-sitter now links via the

*** 4. After retiring 30.2: move to mainline tree-sitter (not yet verified)
Checked against the 0.27.1 bottle's api.h, not by building: it defines
TREE_SITTER_LANGUAGE_VERSION 15, and every ts_* function emacs 31's treesit.c
loads on that path is declared. (=ts_language_version= is gone, but treesit.c
only uses it when built against headers older than 0.25.)
Uninstalling tree-sitter@0.25 does *not* remove the =opt/tree-sitter= shim: brew
resolves it one hop, to =opt/tree-sitter@0.25= rather than the Cellar, so it is not
recognised as belonging to the keg. Remove it by hand, and only while it still
points at the @0.25 keg -- otherwise =brew install tree-sitter= fails.

Uninstall @0.25 last: the 31.1 binary links its library, so emacs will not start
after the uninstall until it is rebuilt.

=gmake distclean= deletes far more than =src/emacs=: native-lisp/ (which the
dump loads at startup), lisp/loaddefs.el and etc/DOC among ~600 files. So the
whole build tree is copied aside first (~430 MB), and every later step is
chained: a failed install or rebuild stops the chain before the uninstall.
#+begin_src sh
[ "$(readlink /opt/homebrew/opt/tree-sitter)" = /opt/homebrew/opt/tree-sitter@0.25 ] \
  && rm /opt/homebrew/opt/tree-sitter
unset PKG_CONFIG_PATH              # mainline is not keg-only
cd ~/bin/emacs-31.1 \
  && brew install tree-sitter \
  && pkg-config --modversion tree-sitter \
  && [ ! -e ~/bin/emacs-31.1.bak ] \
  && cp -Rp ~/bin/emacs-31.1 ~/bin/emacs-31.1.bak \
  && touch ~/bin/emacs-31.1.bak/.backup-complete \
  && gmake distclean \
  && ./configure \
       --with-native-compilation \
       --with-tree-sitter \
       --without-compress-install \
       --disable-gc-mark-trace \
       --with-xwidgets \
  && gmake -j"$(sysctl -n hw.ncpu)" \
  && otool -L src/emacs | grep -q 'opt/tree-sitter/lib' \
  && brew uninstall tree-sitter@0.25
#+end_src
The uninstall only runs once the rebuilt binary links the mainline library. Then
re-run the step 3 checks, and once they pass, delete the backup:
#+begin_src sh
rm -rf ~/bin/emacs-31.1.bak
#+end_src

A leftover =emacs-31.1.bak= stops the chain before the copy, so a second attempt
cannot nest a copy of an already-distcleaned tree inside it. Delete or restore it
first.

If the chain stops after =.backup-complete= is written but before the uninstall,
@0.25 is still installed and the backup runs as it did before. Swap it back; the
check refuses a missing or partial backup, and nothing is deleted until the swap
has worked:
#+begin_src sh
cd ~/bin \
  && [ -e emacs-31.1.bak/.backup-complete ] \
  && mv emacs-31.1 emacs-31.1.failed \
  && mv emacs-31.1.bak emacs-31.1 \
  && rm emacs-31.1/.backup-complete \
  && rm -rf emacs-31.1.failed
#+end_src
If the chain stopped before the marker (at =brew install=, =pkg-config= or during
the copy), =distclean= never ran and the working tree is untouched: just delete
any partial =emacs-31.1.bak=.
Once @0.25 is uninstalled the backup cannot start any more (it links that
library), so from then on the way forward is fixing the rebuild, not restoring.

*** Why tree-sitter 0.25 is the real minimum
configure only requires =tree-sitter >= 0.20.2=, but ABI 15 support is decided at
compile time by the headers emacs is built against:
#+begin_src c
  /* src/treesit.c */
  #if TREE_SITTER_LANGUAGE_VERSION >= 15
    return ts_language_abi_version (ts_lang);
  #else
    return ts_language_version (ts_lang);
  #endif
#+end_src
0.25's api.h is where that constant became 15. Built against anything older,
configure passes and the build succeeds, but grammars built by a current
tree-sitter CLI (ABI 15) are rejected at load time. This shim is also why 31
builds against 0.26+ and 30.2 does not: 0.26 removed =ts_language_version=.

*** What is new in 31 for tree-sitter
Checked against etc/NEWS in the 31.1 release:
- =treesit-auto-install-grammar= :: installs a missing grammar when a tree-sitter
  mode needs it. Defaults to ='ask=; my init.el sets ='always=. The built-in modes
  register their own recipes, pinned to commits, in =treesit-language-source-alist=.
- =treesit-language-source-alist= :: accepts keywords, e.g.
  =(json "https://github.com/tree-sitter/tree-sitter-json" :commit "4d770d3")=
- =treesit-enabled-modes= :: set to t, or to a list, to enable tree-sitter modes
  through =major-mode-remap-alist=.
- treesit-x.el :: =define-treesit-generic-mode=, plus simple generic modes such
  as =gitattributes-generic-ts-mode=.
- Query predicates =:equal=, =:match= and =:pred= are deprecated in favour of
  =:eq?=, =:match?= and =:pred?=. Emacs converts the old names, so existing
  queries still work.

** Verified build recipe (emacs 30.2, Apple Silicon)
This is the recipe that actually produced the emacs 30.2 in use. Confirmed against
~/bin/emacs-30.2/config.log, which shows the working build used a plain configure
line with *no* CFLAGS / CPPFLAGS / LDFLAGS / TREE_SITTER_* overrides at all.

The older notes further down record a long detour chasing tree-sitter flags that
turned out to be unnecessary. See "Known gotchas" below for what was really going on.

*** 1. Prerequisites
#+begin_src sh
# Build toolchain.
#   make          -> gmake. macOS ships GNU Make 3.81 (2006); emacs wants newer.
#   texinfo       -> makeinfo, needed to build the manuals.
#   gcc/libgccjit -> required by --with-native-compilation.
brew install gcc libgccjit make gnutls texinfo autoconf pkg-config

# tree-sitter. The version has to match what the emacs version expects:
#   emacs 30.2 -> tree-sitter 0.25.x
#   emacs 31+  -> will probably want something newer
# Mainline has moved on, so the pin is no longer optional: the unversioned
# formula is 0.26, which removed ts_language_version and cannot build 30.2 at
# all. The versioned formula IS keg-only, which is the source of all the pain in
# the older notes below -- see gotcha #1.
brew install tree-sitter@0.25

# emacs 29 only: jansson, for --with-json. Not needed from emacs 30 on, which
# ships its own JSON parser.
# brew install jansson

# Runtime helpers for my config
brew install ispell    # flyspell needs a spell checker
brew install pandoc    # markdown-mode uses this to preview markdown
brew install graphviz  # org-roam-graph shells out to dot
#+end_src

Because the keg is not symlinked into the prefix, pkg-config finds it only with
PKG_CONFIG_PATH set. Export it in the shell you will run ./configure from, and
keep that shell for step 3. Verify before going further -- this must print a
0.25.x version:
#+begin_src sh
export PKG_CONFIG_PATH="$(brew --prefix tree-sitter@0.25)/lib/pkgconfig"

pkg-config --modversion tree-sitter
#+end_src
If it says "not found in the pkg-config search path", stop and read gotcha #1.
Do *not* reach for TREE_SITTER_CFLAGS.

Note there is no homebrew package to install for --with-xwidgets: on macOS it uses
the system WebKit.framework. It has nothing to do with the =wxwidgets= formula.

*** 2. Get the source
Download a release tag tarball from https://github.com/emacs-mirror/emacs/tags
(upstream is git://git.savannah.gnu.org/emacs.git if you would rather clone).

Unpack it somewhere you are willing to keep long term -- if you go the "run from
the build tree" route in step 5, this directory is where the binary lives.
~/bin/emacs-<version>/ is what I have been doing.

*** 3. Configure
#+begin_src sh
./autogen.sh

# ./configure --help lists everything
./configure \
    --with-native-compilation \
    --with-tree-sitter \
    --without-compress-install \
    --disable-gc-mark-trace \
    --with-xwidgets
#+end_src

That is the whole thing. No flag overrides -- no CFLAGS, CPPFLAGS, LDFLAGS or
TREE_SITTER_*. The one variable that must be set is PKG_CONFIG_PATH from step 1,
which tells pkg-config where to look rather than overriding what it reports; if
this is a fresh shell, export it again before configuring.

What the flags do:
- --with-native-compilation :: bare (= "yes") natively compiles the preloaded lisp
  and JIT-compiles the rest on first use. Passing =aot= instead compiles every lisp
  file in the tree ahead of time: much slower build, no first-use pause later.
- --with-tree-sitter :: needs pkg-config to find tree-sitter (see step 1).
- --without-compress-install :: do not gzip the installed .el files.
- --disable-gc-mark-trace :: about 5% better garbage collection performance. It is
  enabled by default because disabling it makes it harder for emacs developers to
  help track down GC-related bugs.
- --with-xwidgets :: embedded WebKit views, via the system WebKit.framework.
- emacs 29 also needed --with-json; emacs 30 and newer do not.

configure prints a feature summary at the end. Check these lines before building:
#+begin_src
  Does Emacs use -ltree-sitter?                           yes
  Does Emacs support Xwidgets?                            yes
  Does Emacs have native lisp compiler?                   yes
#+end_src
If tree-sitter says "no" here, fix it now -- the build will otherwise succeed
without it and you will not notice until much later.

*** 4. Build
#+begin_src sh
gmake -j"$(sysctl -n hw.ncpu)"
#+end_src

Verify: =src/emacs -Q= starts.

*** Known gotchas
**** 1. keg-only tree-sitter (this is what the older notes were fighting)
tree-sitter@0.25 is a versioned formula, so homebrew does not symlink it into
/opt/homebrew and its headers are not on the default include path. configure's
tree-sitter probe then compiles a test program calling ts_parser_new with no
declaration in scope; clang 16+ treats an implicit function declaration as a hard
error; configure concludes tree-sitter is missing. The clang change is the
messenger, not the bug -- the real problem is the missing -I.

The fix is to let pkg-config find the keg, not to silence the compiler:
#+begin_src sh
export PKG_CONFIG_PATH="/opt/homebrew/opt/tree-sitter@0.25/lib/pkgconfig"

pkg-config --cflags --libs tree-sitter
#   -I/opt/homebrew/Cellar/tree-sitter@0.25/0.25.10/include
#   -L/opt/homebrew/Cellar/tree-sitter@0.25/0.25.10/lib -ltree-sitter
#+end_src
Then run the plain ./configure from step 3, unchanged.

Do *not* set TREE_SITTER_CFLAGS. Per ./configure --help it *overrides* pkg-config
rather than adding to it, so setting it to "-Wno-error=..." deletes the -I path
pkg-config would have supplied. That is exactly the trap in the older notes below:
each override knocked out another flag, which then had to be restored by hand as
CPPFLAGS, then LDFLAGS, then TREE_SITTER_LIBS. PKG_CONFIG_PATH avoids the whole
chain and does not hardcode Cellar paths that go stale on the next upgrade.

***** The opt/tree-sitter shim, and the upgrade that can clobber it
On the machine this recipe was verified on, /opt/homebrew/opt/tree-sitter is a
symlink to another *opt* symlink rather than into the Cellar:
#+begin_src sh
# /opt/homebrew/opt/tree-sitter      -> /opt/homebrew/opt/tree-sitter@0.25
# /opt/homebrew/opt/tree-sitter@0.25 -> ../Cellar/tree-sitter@0.25/0.25.10
#+end_src
Both links carry the same date, so this is most likely left behind by homebrew
migrating the then-unversioned install into the versioned keg. Nothing in this
repo creates it and a fresh machine will not have it, so it is worth recognising
rather than relying on.

While it exists, =brew install tree-sitter= fails outright:
#+begin_src
Error: tree-sitter: /opt/homebrew/opt/tree-sitter@0.25 is not a valid keg
#+end_src
brew resolves an opt path with a single readlink hop, so it lands on the second
symlink, whose grandparent is the prefix rather than the Cellar, and rejects it.
=realpath= follows both hops, which is why pkg-config and the compiler are
perfectly happy and only brew trips over it. Under =set -e= that takes every
later install in the script with it.

The bigger problem is that an emacs built before the migration links the library
*through* that path:
#+begin_src sh
otool -L ~/bin/emacs-30.2/src/emacs | grep tree-sitter
#   /opt/homebrew/opt/tree-sitter/lib/libtree-sitter.0.25.dylib
#+end_src
So anything that repoints =opt/tree-sitter= at the unversioned keg -- a plain
=brew install tree-sitter=, or a =brew upgrade= that pulls it in as some other
formula's dependency -- leaves that binary unable to start, because 0.26 ships
=libtree-sitter.0.26.dylib= and nothing at the old name.

Building with PKG_CONFIG_PATH set, as step 1 now does, is what removes the
dependency: the keg records its own install_name as
=/opt/homebrew/opt/tree-sitter@0.25/lib/libtree-sitter.0.25.dylib=, so a fresh
link picks up the versioned opt path, which brew owns and keeps pointing at the
right keg. Check an existing binary with the otool line above -- if it names
=opt/tree-sitter= rather than =opt/tree-sitter@0.25=, it is still leaning on the
shim and wants a rebuild.

**** 2. brew upgrade gcc can break native compilation
emacs links against a specific libgccjit. After upgrading gcc, NATIVE_COMP will
still appear in system-configuration-features (it was compiled in) while
(native-comp-available-p) returns nil and you get libgccjit errors at runtime.
The fix is to rebuild emacs. This is why step 6 checks the predicates and not
just the feature list.

**** 3. Dead ends -- do not re-investigate these
- Building with homebrew gcc instead of clang: no. The macOS build is a Cocoa/NS
  build and is partly Objective-C, which homebrew's gcc does not support.
- CC=clang-16: no such binary. Apple's clang is not installed under versioned names.
- Downgrading to clang 15: not feasible with Apple's toolchain, and unnecessary --
  see gotcha #1 for the actual cause.
- brew install wxwidgets: unrelated to emacs. "xwidgets" is an emacs feature name;
  the string "wxwidgets" does not appear anywhere in emacs configure.ac.

* Java
** Current recipe
The old notes below are broken: they install =openjdk@21= but every path that
follows points at the *unversioned* =openjdk= keg. Those caveats came from
=brew info openjdk=, not =brew info openjdk@21=, and the two are different
prefixes. Following them symlinks a different JDK than the one you installed,
or nothing at all.

Symptom, and the state of this machine as of <2026-07-30>: java is not working.
=/Library/Java/JavaVirtualMachines/= is empty, =/usr/libexec/java_home= reports
"Unable to locate a Java Runtime", and =java -version= fails -- even though
openjdk plus @23, @24, @25 and @26 are all installed. They are keg-only, so
installing them registers nothing with macOS on its own.

*** Install
Pick the version deliberately and use it consistently. Substitute for NN below
(the machine currently has 23, 24, 25, 26; there is no 21 despite what the old
notes say):

#+begin_src sh
brew install openjdk@NN

# Everything after this must use the SAME @NN. Get the prefix from brew rather
# than typing it, so the two cannot drift apart:
JDK="$(brew --prefix openjdk@NN)"

# Register it with macOS so /usr/libexec/java_home and the system wrappers see it
sudo ln -sfn "$JDK/libexec/openjdk.jdk" /Library/Java/JavaVirtualMachines/openjdk-NN.jdk
#+end_src

Naming the symlink openjdk-NN.jdk rather than openjdk.jdk lets several JDKs be
registered at once and selected with =/usr/libexec/java_home -v NN=.

openjdk is keg-only -- homebrew does not symlink it into /opt/homebrew, because
macOS ships similar software and installing in parallel causes trouble. That is
why the registration step above is required and not optional.

*** PATH
The old notes say to =echo ... >> ~/.zshrc=. Do not: sync-dotfiles.sh copies
Dotfiles/zshrc over ~/.zshrc, so that gets wiped on the next sync. Put it in
=Dotfiles/zshrc= and re-sync.

Note Dotfiles/zshrc:49 currently reads
=export PATH="/usr/local/opt/openjdk/bin:$PATH"=. /usr/local is the *Intel*
homebrew prefix; on Apple Silicon it is /opt/homebrew, and /usr/local/opt/openjdk
does not exist here. The line is a harmless no-op rather than the cause of the
breakage above, but it has never done anything on this machine. Replace it with
the versioned path when you decide which JDK should be the default:

#+begin_src sh
export PATH="/opt/homebrew/opt/openjdk@NN/bin:$PATH"
#+end_src

Or leave PATH alone and select per-shell with =export JAVA_HOME="$(/usr/libexec/java_home -v NN)"=.

For compilers to find the headers:
#+begin_src sh
export CPPFLAGS="-I/opt/homebrew/opt/openjdk@NN/include"
#+end_src

*** Verify
#+begin_src sh
java -version                    # should print the version, not an error
/usr/libexec/java_home -V        # should list the JDK you registered
ls /Library/Java/JavaVirtualMachines/
#+end_src

An empty /Library/Java/JavaVirtualMachines means the =ln -sfn= step above did not
happen. That is the current state, and it is what "Unable to locate a Java
Runtime" is telling you -- the JDK is installed, macOS just cannot see it.

** Original notes (kept for reference -- paths do not match the install)

* mise
** Current recipe
Unlike the emacs section, this one is *not* verified against a working setup --
mise is not installed on this machine as of <2026-07-30>. Checked against upstream
docs only.

*** Install and activate
#+begin_src sh
brew install mise
#+end_src

The activation line goes in =Dotfiles/zshrc= in this repo, *not* in ~/.zshrc:

#+begin_src sh
eval "$(mise activate zsh)"
#+end_src

then re-run ./sync-dotfiles.sh and open a new shell.

This is the important correction to the old notes below, which say
=echo 'eval "$(mise activate zsh)"' >> ~/.zshrc=. sync-dotfiles.sh does
=cp ~/src/dotfiles/Dotfiles/zshrc ~/.zshrc=, so anything appended to ~/.zshrc
directly is silently wiped the next time the dotfiles are synced.

*** Install tools -- mind the -g
#+begin_src sh
# GLOBAL: writes ~/.config/mise/config.toml. This is what you want for machine setup.
mise use -g erlang@28.4.1
mise use -g elixir@1.19.5

# or track latest
mise use -g erlang@latest
mise use -g elixir@latest

# PER-PROJECT: writes ./mise.toml in the current directory
cd ~/src/someproject && mise use elixir@1.19.5
#+end_src

=mise use= without =-g= writes a mise.toml *in the current directory*. The old
notes below omit the flag, so following them from the home directory leaves a
stray ~/mise.toml and no global default.

*** Verify
#+begin_src sh
mise doctor        # run after activation, not before -- it checks the shell hookup
mise ls            # installed tools, and which config file each came from
which erl elixir
#+end_src

* asdf
** Current recipe (asdf 0.16+, the Go rewrite)
Also not verified on this machine: asdf is not installed, and the activation line
in Dotfiles/zshrc:52 is commented out. From upstream docs.

asdf was rewritten in Go in v0.16.0 (2025-01-30). The notes below pin
=--branch v0.14.0=, the old shell implementation, and every shell-integration
instruction in them is obsolete. If you have moved to mise (see that section)
you probably do not need asdf at all -- this is here for projects that require it.

*** What changed in 0.16
| old (0.14, shell)         | new (0.16+, Go binary)     |
|---------------------------+----------------------------|
| . "$HOME/.asdf/asdf.sh"   | removed; put shims on PATH |
| asdf global <tool> <ver>  | asdf set --home <tool> <ver> |
| asdf local <tool> <ver>   | asdf set <tool> <ver>      |
| asdf plugin-add           | asdf plugin add            |
| git clone a tagged branch | brew install asdf          |

All hyphenated subcommands lost their hyphen, not just plugin-add.

*** Install
#+begin_src sh
brew install asdf
#+end_src

The old =brew install coreutils curl git= line was for the shell implementation.
The Go binary does not need coreutils.

*** Shell setup
In =Dotfiles/zshrc= -- not ~/.zshrc, which sync-dotfiles.sh overwrites -- replace
the commented-out asdf.sh line with:

#+begin_src sh
export PATH="${ASDF_DATA_DIR:-$HOME/.asdf}/shims:$PATH"
#+end_src

ASDF_DATA_DIR defaults to $HOME/.asdf, so setting it explicitly is optional; the
shims directory on PATH is the part that matters. Confirm with =asdf info=.

The completions advice below references =$ASDF_DIR/completions=. ASDF_DIR belonged
to the shell implementation. Use =asdf completion zsh= instead, but check
=asdf completion --help= against the installed version before wiring it into zshrc
-- I have not verified the exact invocation.

The old notes also warn that compinit must come *below* the asdf sourcing. In
Dotfiles/zshrc compinit is at line 44 and the asdf line at 52, i.e. already the
opposite order, so that advice was being violated anyway. Moot under 0.16, which
has no asdf.sh to source, but relevant if you ever go back to 0.14.

*** Erlang/Elixir under 0.16
The Erlang/Elixir subsection below still uses 0.14 syntax. Translated, with
versions bumped to match the mise section:
#+begin_src sh
asdf plugin add erlang
asdf plugin add elixir

asdf list all erlang
asdf list all elixir

asdf install erlang 28.4.1
asdf set --home erlang 28.4.1
asdf install elixir 1.19.5-otp-28
asdf set --home elixir 1.19.5-otp-28

mix local.rebar --if-missing --force

Elixir builds from the asdf plugin are suffixed with the OTP major they were
compiled against, so the =-otp-NN= has to track the erlang version. Run
=asdf list all elixir= for the suffix that actually exists -- I have not confirmed
1.19.5-otp-28 is published.

The wxwidgets note in the old subsection is correct and still applies: Erlang's
observer and debugger are wxWidgets apps.

Reference: https://asdf-vm.com/guide/upgrading-to-v0-16.html

** Original notes (kept for reference -- asdf 0.14, superseded)
See https://asdf-vm.com/guide/getting-started.html

brew install coreutils curl git

git clone https://github.com/asdf-vm/asdf.git ~/.asdf --branch v0.14.0

Add the following to ~/.zshrc:

. "$HOME/.asdf/asdf.sh"

Completions are configured by either a ZSH Framework asdf plugin or by adding the following to your .zshrc:

#+begin_src
# append completions to fpath
fpath=(${ASDF_DIR}/completions $fpath)
# initialise completions with ZSH's compinit
autoload -Uz compinit && compinit

#+end_src

if you are using a custom compinit setup, ensure compinit is below your sourcing of asdf.sh
if you are using a custom compinit setup with a ZSH Framework, ensure compinit is below your sourcing of the framework
